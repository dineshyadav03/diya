# Diya review, 2026-10-27: where we stand, what is wrong, what next

**The goal the owner set today:** "Diya has to be a complete Hark Pro, with the local model." Hark Pro (as the owner pasted it): one ongoing chat with memory; a cloud computer ("Handoff") that does website actions; direct connections to services; a **Home of action cards** that notices useful next steps and offers to act; Projects; a secure vault; spending permissions; web, iOS and Android.

Everything below comes from the database, the code and the screens, not from the task sheet. Where it is only inferred, it says so (section 9).

## 1. Verdict, in plain words

1. **A lot is built and very little is felt.** About half of Hark Pro's list exists in some form. The two parts that make Hark *Hark* do not: a **Home that notices and offers to act**, and **Handoff** (doing things on websites).
2. **We have been building a shelf, not the thing.** 127 modules, 224 test files, 92 design documents, a 298-row task sheet, and the owner used it seriously on **3 days out of the last 10**.
3. **Every problem the owner hit today has one cause:** we gave the 4B model too much to decide. It got all the facts (so it mentions the dog), 49 tools (so a reply took 5 to 15 minutes) and the date maths (so "next Tuesday" came out as a Sunday). We patched the symptoms. The project's own rule, *code decides, the model only words it*, was applied unevenly.
4. **The DeepSeek harness is 96% of the repository and nothing uses it.** It is the one thing in the repo that could become Handoff, but only if a 4B model can drive it, which nobody has measured.
5. **The UI looks like a settings app**, because it is 16 pages of settings and lists. Hark's UI is one Home of cards.
6. **Complete Hark Pro with a 4B local model is not possible. About 60% of its practical value is.** The rest (open-ended website actions) can only be done as scripted flows, one chore at a time. See section 7.

## 4. What we are doing wrong

1. **Measuring progress by the task sheet.** "Done" means a test against a stand-in passed. The database says 0 tasks, 0 automations, 0 phone devices, 2 actions. The owner cannot see most of the work, so "136 done" feels like zero.
2. **Fixing the model's mistakes after it makes them.** The dog filter hides a sentence the model should never have been invited to write. The date answer, the 49 tools and all-facts-always are the same mistake: asking a 4B model to do what code does better.
3. **Research without a decision.** 34 research entries, 22 reviews, 92 docs. The owner said "stop research, start using" on 14 Oct. Then came a 298-row sheet.
4. **Copying a 344-package framework in and never running it.** See section 5.
5. **Redesigning the look three times without deciding what the screen is for.** Tokens, a screenshot rig and contrast tests all exist. None of them can tell you that the front page should be a Home of cards.
6. **The cost of how we work.** Full test suites on a laptop with 200 to 800 MB free, very long chats, weekly limit at 68%. The owner said they feel overwhelmed. That is a product risk: a tool you dread working on does not get used.

**What is right, and stays:** local-first and private; approvals by exact hash; reviewed memory with a record of how Diya knows things; code-first routing; Google really connected (14 cards, read calls verified); the speed fix (a turn is now 17 seconds, model on the GPU).

## 5. The DeepSeek harness

- **What is here:** a plain copy, 16,286 files, 58 packages in `packages/` plus `apps/` (cli, web, desktop). Diya's code touches it in **two comment lines** (`diya_feedback.py`, `diya_toolguard.py`: ideas borrowed, no code). Phases 1 to 4 of `docs/DSH_PLAN.md` are **not started**. Phase 1 (`docs/DSH_PHASE1.md`) is a runbook for the owner and has not been run.
- **Why it is worth a look:** it has what Diya lacks for Handoff (`browser-use`, `computer-use`, `schedule`, `mcp`, `credentials`, `interaction` for approvals, `compaction`).
- **Why not to wire it in blind:** it is a developer preview with, in its own words, no security audit; its base prompt alone is about 30 KB of source against a 16,384-token window; it was built for frontier models; nobody has measured whether `diya-chat` can drive its tool loop at all; Windows and Ollama support is "probably configurable", unverified.
- **I cannot run it.** It installs hundreds of third-party packages and runs model-written commands. The rule is that Claude does not execute downloaded third-party code, even when asked. The owner runs Phase 1 in Docker, per `docs/DSH_PHASE1.md`, with no credentials.
- **Verdict:** one evening, owner-run, ten questions, then decide by the numbers: first words in under 30 seconds and no invented tool use means keep going; otherwise drop it. Until then it is dead weight: it is 96% of the files, slows every git and OneDrive sync, and makes "what is Diya?" unanswerable. After the try, move `harness/` out of the repo (the plan says a pinned copy is already at `C:\Users\dines\dsh-copy`). Needs the owner's yes.

## 6. Why the UI looks ugly

I captured the live app with the design rig (stub data, not the real database; 13 Oct screenshots are in `docs/`).

- **Two different looks exist.** The 13 Oct screenshots are a dark sidebar with 15 nav items. The live app today is a pastel gradient with a hamburger and a three-pill top bar. The design has not settled.
- **It is a settings app.** 16 pages, each a list or a form, with long explanatory paragraphs ("Nothing here is written by Diya's model...") and heavy outlined boxes, lowercase serif headings.
- **Nothing answers "what should I do now?"** Hark's front door is a Home of cards with one button each. Diya's front door is a chat box and a menu.
- **The fix is not a restyle.** One Home, the chat docked under it, four places in total (Home, Chat, Memory, Settings with everything else inside). Make a mock-up with fake data first, let the owner choose, then build once.

## 7. What a 16 GB laptop and a 4B model cannot do

Measured today: the model reads at about 62 tokens a second on the GPU, a turn is about 17 seconds, free RAM is often under 1 GB.

- **Can:** find things by code, pick a date, pick a few facts, classify a message, pull fields out of an email, word one short line from structured data, draft a reply for approval.
- **Cannot, reliably:** choose among dozens of tools, do date arithmetic, plan a ten-step job, read a web page and decide where to click, hold a long context.
- **So:** every Hark feature must be "code finds and acts, the model words", with approvals. Open-ended Handoff does not fit. A few fixed website flows do.
- A bigger local model does not fit 16 GB comfortably. The Mac mini is deferred.

## 8. The plan: five items, in order

1. **Stop the model deciding what code can (1 to 2 days).** (a) Tell it only the facts that match the message, plus name and allergies: first compute the 13 accepted facts' embeddings, since none exist. (b) Dates by code: "next Tuesday" gives 3 Nov, said in the answer. (c) Tools only when asked. *You will see:* no dog, no teal, right dates, faster replies.
2. **A Home of action cards, and one clean look.** Cards from code: next calendar event, an email waiting for a reply, a reminder due, an open memory question; each with a button that stages the action in the existing approvals. Delete the "nothing on your list" cards. Four places, not sixteen. A mock-up first. *You will see:* open Diya and 3 to 6 real things, each with "Do it" and "Not now".
3. **Use it for 7 days on your phone.** Switch on one phone channel (Telegram or Web Push over a VPN), do the real-account tries in `docs/GOOGLE_LIVE_SMOKE.md`, and judge by the database, not the sheet. *You will see:* tasks, approved actions and phone messages in double digits, or an honest reason they are not.
4. **One Handoff job, scripted.** Pick the one website chore you repeat most (a bill, a reorder, a booking). Build it as a fixed browser flow with approval, a spending cap and the vault; the model only supplies the details. In parallel you run the harness Phase 1 evening and we decide from the numbers.
5. **Cut.** No new research, no new task-sheet rows, no new design docs. Move the 37 modules the server does not use (benches, milestone demos) into `tools/`. Move `harness/` out after the try. Full tests only on GitHub.
